How swapping works

One question this diagram answers: what stays fixed when we add a second code? Fixed = action transfer, report tree shape, UI, WASM command. Swappable = clause math, classification, φ/Ω or γM, clause IDs, example corpus.

Rust surface (shared vs profile)

Shared (never code-specific)

  • DesignDemand — N, Vy, Vz, My, Mz, T from one combination/station
  • MemberContext — L, Ky/Kz, Cb, bracing, material Fy/Fu, section props
  • CheckOutcome — pass/fail/unsupported/indeterminate + utilisation + intermediates
  • DesignRun — header (profileId, modelHash, resultId) + ordered check tree
  • Mandatory-gate: any mandatory UNSUPPORTED ⇒ overall UNSUPPORTED

Per profile (swap unit)

  • profile_id() e.g. aisc-360-22-lrfd
  • Metadata: standard, edition, method, source hashes, clause map version
  • applicability(&ctx) -> Apply — reject torsion / non-W / etc.
  • run_checks(&demand, &ctx) -> Vec<CheckOutcome>
  • Dossier under docs/code-profiles/<id>/ + fixtures under fixtures/design/<id>/

Layout proposal: keep workbench-design as the orchestrator + mechanics screen; add workbench-design-aisc36022 (or crates/design/profiles/aisc36022) so Eurocode does not drag AISC into the WASM binary until enabled — or feature-flag profiles. Prefer feature flags / separate crates over a giant match statement.

Proposed delivery slices

  1. A
    M07-A Profile skeleton

    CodeProfile trait, registry, empty designProfiles until lock, evaluateDesign dispatches by id, UNSUPPORTED for unknown/disabled. ADR + dossier skeleton under docs/code-profiles/aisc-360-22-lrfd/. No clause math yet.

  2. B
    M07-B Resource acquisition

    Download AISC 360-22 + Design Examples v16 (+ errata) + shapes DB to an ignored local vault; write SHA-256 into resources.lock.json; record rights = acquired-for-implementation, not redistributed. Extract fixture JSON from examples (our numbers, not copyrighted prose).

  3. C
    M07-C Clause families (S2)

    Classification → tension → compression (E3) → flexure (F2/F…) → shear (G) → H1 interaction. Each check: clause id, intermediates, boundary tests. Fail-closed on torsion / non-prismatic / missing Lb.

  4. D
    M07-D Product journey

    Model-derived + standalone inputs; Screen 04 UI; section change → reanalyse → redesign; report with clause trail; ≥3 pass + ≥3 fail complete members; capability ledger updates.

  5. P
    M07-parent

    Same-build verifier packaging. No second code required for acceptance.

Resource handling (rights-aware)

  • R-CODE-STEEL: ANSI/AISC 360-22 PDF from aisc.org — free download; hash in lockfile; do not commit PDF.
  • R-STEEL-EXAMPLES: Manual Companion Design Examples v16.0 (+ June 2025 errata) — free; fixture tables derived into repo JSON.
  • Shapes: AISC Shapes Database v16 as optional catalogue input; section props still validated in Rust.
  • Formulation dossiers cite clause numbers and our independent recomputation; they do not paste copyrighted paragraphs.

Risks

  • Invented clauses. Agents must not code from memory/snippets. Gate implementation on lockfile + dossier. Mitigate: checklist in skills/prokon-numerical.
  • Scope creep to “all AISC”. Reject unsupported shapes loudly; keep capability ledger honest.
  • Envelope as demand. Already forbidden — reuse simultaneous-combination rule from analysis.
  • PDF in CI. Examples must be reconstituted fixtures; CI must not require private PDFs after lock.
