Structural Workbench · design packages

How to make “any code later” boring.

Goal: adding AISC, Eurocode, ACI, CSA… is a new profile crate + resource lock + fixtures, not a fork of the solver, UI, or report pipeline. Analysis stays code-agnostic; compliance stays pluggable and fail-closed.

today mechanics-v1 stress screen in crates/design · blocked M07 until standard + examples lock · hook ready evaluateDesign / designProfiles[]

1. What already exists (don’t reinvent)

SPEC §9 + PROTOCOL §5 already define the shape. Kernel today refuses design until a profile is enabled.

Evidence: crates/wasm-api empty designProfiles; evaluateDesign hard-fails; SPEC already mandates pure Rust checks + pinned profile metadata.

2. Target shape — profile plugins on a frozen contract

One shared DesignHost owns action transfer, roll-up status, and reporting. Each code is a versioned plugin that never touches stiffness.

Adding a code = new crate (or feature) that implements one trait + ships its clause map and example corpus. Host + PROTOCOL check tree stay frozen.

3. The frozen seam (what every profile must speak)

LayerOwnsMust not own
Analysis Geometry, loads, solve, recovery, envelopes, hashes fy, φ, γ, classification, utilisation
Action transfer (host) Pick simultaneous action vector from a real case/combination at station/side Envelope max-of-max as if concurrent
CodeProfile (plugin) Applicability, resistance, intermediates, clause/formula IDs, mandatory set Mutating the model or inventing missing actions
Ledger + UI Advertise enabled profiles; refuse unsupported domains; render check tree Hard-coding clause text or “green” without mandatory coverage
Resource lock Edition, annex, content hash, rights, example IDs URLs alone; OSS formula libs as sole authority

Check object shape already fixed in PROTOCOL §5: pass | fail | unsupported | indeterminate with nullable numerics never coerced to 0.

4. Recipe to add a future code (checklist)

  1. Amen the profile ID: en1993-1-1:2005+ukna or aisc-360-22-lrfd — never bare “Eurocode”.
  2. Lock resources into resources.lock.json (standard hash + worked examples). Gate stays closed until this exists.
  3. Write dossier under docs/code-profiles/<id>/ (clause map, branches, unsupported predicates).
  4. Implement crate workbench-design-<id> behind Cargo feature; register in DesignHost.
  5. Fixtures: ≥3 pass, ≥3 fail, boundary cases per mandatory check family; independent expected values.
  6. Advertise only after verification: designProfiles[] + capabilities.json row with comparisonStatus still honest.
  7. UI/report: no new screens required beyond selecting profileId and rendering the check tree.

5. Packaging options

A · Trait + Cargo features recommended

One host crate; each profile is workbench-design-* enabled by feature. WASM builds ship only enabled profiles (size control).

  • Pros: clear deps, optional WASM slices, matches Rust ownership rule
  • Cons: rebuild to add a profile to a given release

B · Dynamic WASM modules

Load profile WASM at runtime from a URL/registry.

  • Pros: hot-add codes without app rebuild
  • Cons: fights CSP / “no dynamic remote modules” MVP constraint; harder hash-binding

C · Data-driven rule tables only

JSON coefficients + generic engine, no per-code Rust.

  • Pros: looks “easy” to extend
  • Cons: collapses on branching codes; invents a mini-language; weak clause evidence

D · Wrap OSS libs (Blueprints / eurocodepy) as oracles

Native CI oracle only; product path still Rust profile + locked standard.

  • Pros: extra cross-check once resources exist
  • Cons: cannot replace authoritative text/examples; Python not in WASM MVP

Open standards we can piggyback?

Short answer: yes for plumbing, no for the legal text of the design code.

piggyback Open contracts & data

  • Our own PROTOCOL check tree + profile metadata (already the extension seam)
  • Section catalogues with clear licences (e.g. public shape tables) as inputs, not as code authority
  • Independent oracles we already use (OpenSees) and optional OSS formula libs as cross-checks
  • Later exchange: DXF/IFC schemas (open), mapped through exchange — still not a member-check code

cannot replace Design code authority

  • EN 1993 / EN 1992 / AISC 360 / ACI 318 text + official examples are copyrighted
  • No open “Eurocode pack” that satisfies R-CODE-STEEL (edition hash + rights + worked examples)
  • Blueprints / eurocodepy / pyaisc = secondary implementations, not the standard

Architecture implication: piggyback the plugin contract (open, ours). Pin each jurisdiction’s document separately when you have lawful access. Don’t wait for a mythical open EN/AISC text dump.

7. Risks if we skip this

  • Hard-coding AISC types into assembly / UI → Eurocode becomes a rewrite.
  • Treating OSS formula packages as the standard → rights + verification failure.
  • Advertising “Eurocode” without annex/edition → SPEC violation.
  • Shipping all world codes in one WASM blob → download/memory pain; feature slices fix this.
