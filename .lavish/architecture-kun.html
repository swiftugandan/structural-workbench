Proposed approach

Architecture I'd actually run

  1. Runtime spine stays. Rust crates own model/units/assembly/solver/results/design/exchange; one Worker owns the project; JS only formats and CAD-previews; WebGPU rebases f64→f32 for display.
  2. Protocol is the real API. Treat contracts/ + worker ops as the product boundary. Anything that can't be expressed as a revision-aware command is not a feature yet.
  3. Split workers on schedule, not vibes. Spec already says model Worker vs analysis Worker by M03. Do that when edit-during-solve is real — not as premature microservices.
  4. Design codes are plugins with resource gates. Keep crates/design empty-ish until clause text + examples are lawful. Never invent jurisdiction compliance.
  5. Thin the JS shell. app.js is already the place complexity hides. Carve command forms / results / persistence behind the existing module seams before M02 load-combination work lands.
  6. Delivery OS > org chart. AGENTS.md + delivery/state.json + hash-bound evidence is the operating system. For high-stakes merges I'd gate through no-mistakes. I would not stand up firstmate until parallel-session juggling actually hurts.
  7. Parity is a matrix, not a vibe. Workflow / numerical / code / exchange / ops stay separate rows. No single “% PROKON” number. Ever.
Hard take: finishing another ribbon polish while M00/M01 parent acceptance is blocked on a real-GPU runner is optimizing the wrong objective. Independent DAG work is fine; calling it milestone acceptance is not.

Decision

Three directions

A · Spec-faithful deepen

chosen

Keep runtime. Ship M02 loads/combinations on the protocol. Thin app.js only as needed for that slice. Do not waive platform/CUA blockers.

Cost: slower “demo wow.” Gain: trustworthy calc product.

B · Kernel-first library

Not chosen. Keep CLI/oracle strength inside the existing crate graph without demoting the browser client.

C · Framework rewrite

Rejected. Spec forbids it; frameworks burn agent context without buying f64 truth.

Next slice · M02

Loads & combinations — execution spine

Verified-MVP rule: a combination is not “done” until oracle + WASM + browser journey agree on the same modelHash.

  1. Extend contracts for combination provenance (case ID × factor, reject duplicates/nesting per §6.1).
  2. Implement combination application only in Rust assembly/results recovery — envelopes carry governing case/combination + station.
  3. Add analytical + oracle fixtures before UI; WASM must match native within existing tolerances.
  4. UI: create/edit cases and combinations via worker commands; display only.
  5. Browser journey: assign loads → combine → analyse → inspect envelope → save/reopen → report excludes stale results.
